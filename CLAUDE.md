## Project Overview

This project builds a **Whitespace and Cross-Sell Opportunity Analyzer** for SAP sales teams. The goal is to identify accounts that own products in some SAP Solution Areas but have zero coverage in others ("whitespace"), then rank those gaps by outside-in wallet opportunity, industry fit, and territory ownership.

Business requirements are in [archive/business_requirements.md](archive/business_requirements.md).

Weekly data download instructions (SAC report URLs and required filter settings) are in [docs/weekly-data-update.md](docs/weekly-data-update.md).

The analyzer is a single-page interactive HTML document (`output/whitespace-analyzer.html`) generated by a three-script Python pipeline.

## Running the Pipeline

**Weekly update — point at a dated input folder:**
```bash
python3 run_pipeline.py --input-dir input/2026-08-10/
```
Auto-discovers all source files by filename pattern; derives `--snapshot-date` from the folder name. All outputs written to `output/2026-08-10/` (i.e. `data.json`, `clusters.json`, `whitespace-analyzer.html`, `version.json`).

**Shortcut with example data (defaults):**
```bash
python3 run_pipeline.py
```
All source file paths default to `example-data/` and `reference-data/`. Override with `--am`, `--am-tp`, `--iaa`, `--tao`, `--adrm`, `--spi`, `--ref`, `--sah`, `--out`. Pass `--no-cache` to re-fetch CDN assets. Pass `--snapshot-date YYYY-MM-DD` to set the date shown in the dashboard header and to route outputs into `output/<YYYY-MM-DD>/`.

**Individual steps:**
```bash
python3 ingest.py \
  --am    example-data/MW_MU_AM_2026-07-06.csv \
  --am-tp example-data/MW_MU_AM_TP_2026-07-08.csv \
  --iaa   example-data/MW_MU_IAA_2026-07-06.csv \
  --tao   example-data/MW_MU_TAO_2026-08-17.csv \
  --adrm  example-data/MW_MU_ADRM_2026-07-06.csv \
  --spi   example-data/MW_MU_SPI_2026-07-06.csv \
  --ref   reference-data/SAP_Industry_Solution_Reference.xlsx \
  --sah   "reference-data/Copy of Solution Areas and Logical Products 2026 - update.xlsx" \
  --out   output/data.json

python3 analyze.py \
  --data output/data.json \
  --out  output/clusters.json

python3 build.py \
  --data     output/data.json \
  --clusters output/clusters.json \
  --out      output/whitespace-analyzer.html
  # --template horizon-dashboard-template.html  (alternate SAP Horizon-themed template)
  # --no-cache                                   (re-fetch CDN assets; cached in .cdn-cache/)
```

Requires `pandas` and `openpyxl`.

> **`--input-dir` override gotcha:** File flags are only treated as explicit overrides when their value *differs* from the argparse default. If you want to pin one source file while using `--input-dir`, point it at a non-default path (e.g. `--am /abs/path/to/file.csv`). Passing the default path alongside `--input-dir` will not prevent auto-discovery from overwriting it.

**Overriding intermediate output paths** (`run_pipeline.py` only):
```bash
python3 run_pipeline.py --input-dir input/2026-08-17/ \
  --data output/custom/data.json \
  --clusters output/custom/clusters.json \
  --out output/custom/whitespace-analyzer.html
```

**Regenerating the reference file** (run once when the industry solution reference needs to be rebuilt):
```bash
python3 tools/migrate_reference.py
```

**Building the industry reference from scratch** (builds `SAP_Industry_Solution_Reference.xlsx`):
```bash
python3 tools/build_industry_reference.py
```

## Data Source Joins

### Account / Planning Entity ID

All four transactional sources share a single account key, but with different column names and normalizations:

| Source | Raw Column | Rename | Normalization |
|--------|-----------|--------|---------------|
| **IAA** | `Planning Entity ID` ¹ | — | `.str.strip().str.lstrip("0")` (strips leading zeros) |
| **AM** | `Planning Entity ID` ¹ | — | `.str.strip().str.lstrip("0")` (strips leading zeros) |
| **ADRM** | `Planning Entity ID` ¹ | — | `.str.strip().str.lstrip("0")` (strips leading zeros) |
| **TAO** | `Account ID` | → `Planning Entity ID` | `.astype(str).str.strip()` |

¹ All three CSVs carry a UTF-8 BOM prefix (`﻿`) on the first column name, stripped at load time.

IAA is the master account list. Accounts in AM/TAO/ADRM not present in IAA are dropped. Accounts in IAA with no AM coverage are classified as prospects.

> **Watch out:** IAA, AM, and ADRM all strip leading zeros; TAO does not. The new IAA format (as of 2026-06-30) zero-pads IDs to 10 digits — `load_iaa()` strips them to match TAO.

### Solution Area Names

Each source encodes solution area names differently:

| Source | L1 Column | L2 Column | Code encoding |
|--------|----------|----------|---------------|
| **AM** | `Solution Area Level 1` | `Solution Area Level 2` | `"Finance and Spend Management (FISP)"` — name + code in parens |
| **ADRM** ² | `Solution Area L2` ← actual L1! | `Solution Area L3` ← actual L2! | `"Finance and Spend Management (FSM)"` — name + code in parens |
| **TAO** | `Solution Area` | `Sub Solution Area` | `"Finance and Spend Management"` — bare name, no code |
| **ISR** (`SAP_Industry_Solution_Reference.xlsx`) | `Solution Area L1` | `Solution Area L2` | bare name, no code |
| **SAH ref** (`Copy of Solution Areas and Logical Products 2026 - update.xlsx`) | `SolAr 2026` | `Sub-Solution Area 2026` | bare name, no code |

> ² **ADRM column naming is off by one level.** The column labeled `Solution Area L1` always contains the constant `"Solution Area Hierarchy 2026"`. The column labeled `Solution Area L2` is the actual SAH L1. The column labeled `Solution Area L3` is the actual SAH L2. `ingest.py` reads `Solution Area L2` as L1 — this is correct but the source file labeling is misleading.

**Normalization before joins:**
- AM and ADRM: `strip_code()` removes parenthetical codes — `"Finance and Spend Management (FISP)"` → `"Finance and Spend Management"`
- TAO and reference files: no stripping needed; names are already bare
- Legacy reference entries: `_normalize_ref_sah()` maps stale L1/L2 codes via `LEGACY_SAH_NORM` dict

**ADRM L2→L1 rollup:** ADRM pipeline data is at SAH L2 granularity. `build_l2_to_l1()` inverts the SAH hierarchy to produce `{l2_name → l1_name}`; `build_pipeline_index()` uses this to roll each row up to L1 before storing in the pipeline index.

**TAO L2→L1 rollup:** TAO data is at SAH L2 granularity. `build_tao_index()` sums gap/wallet/acv/acv_at_risk/cy/cy1 across all L2s per L1, and stores the representative row (highest-gap L2) for priority_score/strategy. The raw L2 data is preserved in `tao_l2_index`.

### Industry → Reference Solutions

TAO `Industry` (raw string) is the only bridge to the reference data:

```
TAO.Industry → INDUSTRY_CROSSWALK → SAP_Industry_Solution_Reference.xlsx "Industry"
```

`INDUSTRY_CROSSWALK` (24 entries in `ingest.py`) handles consolidations: `"Banking"` + `"Insurance"` → `"Financial Services"`, `"Healthcare"` + `"Life Sciences"` → `"Life sciences & healthcare"`, `"Media"` + `"Sports and Entertainment"` → `"Media, sports & entertainment"`. Accounts with no TAO record get no `industry_bucket` and therefore no applicable products.

### Product Names (AM ↔ SAH Reference)

AM `Logical Product` values (e.g., `"SAP ERP (LPR246)"`) are resolved to external product names via `build_product_name_map()`, which reads `Product Key` and `External Product Name` columns from the SAH Excel's `Products` sheet. The parenthetical code in the AM value is matched to `Product Key`.

## Core Data Model

- **Customer**: `{customer_id, name, industry, SIC, MU, Sales_Office, Sales_Group}`
- **ProductInstance**: `{customer_id, product_id, status ∈ {live, project, shelfware}}`
- **SAH hierarchy**: L1 → L2 → L4 (Solution Area hierarchy); sourced from `Copy of Solution Areas and Logical Products 2026 - update.xlsx` Products sheet
- **Whitespace**: a customer × L1 pair where the customer is not a prospect and has zero live/project coverage in that L1

## Key Business Logic

- **Coverage**: a customer "covers" SAH L1 X if any product under X is present with status ∈ {live, project, shelfware}
- **Cross-sell whitespace**: baked at ingest using live/project only; `effectiveWs(a)` in the dashboard nulls out L1s where the account has shelfware-only coverage (`cov_any[i] && !cov[i]`)
- **Industry crosswalk**: TAO `Industry` values → Reference file industry buckets via `INDUSTRY_CROSSWALK` dict in `ingest.py`
- **Pipeline index**: ADRM data is at L2; `build_l2_to_l1()` in `ingest.py` maps it up to L1 using the SAH hierarchy before storing in `data.json`
- **TAO index**: TAO data is at L2; `build_tao_index()` sums gap/wallet to L1 and preserves per-L2 detail in `tao_l2`
- **Currency**: all monetary values in KUSD (`EUR_TO_USD = 1.16`); TAO gap/wallet are KEuro × rate; ADRM `Total @ FC` is Euro ÷ 1000 × rate
- **Priority normalization**: TAO `Sales Priority` strings (`"Very High"`, `"High"`, `"Medium"`, `"Low"`, `"Very Low"`) are normalized to `"1 Very High"` … `"5 Very Low"` via `SALES_PRIORITY_MAP` in `ingest.py`; the dashboard `PRI_ORDER` and `prioBubble()` depend on this numeric-prefix format
- **No automated test suite**: the validation framework (`validate.py`) is the test harness; running the pipeline is the integration test

## Validation Framework (`validate.py`)

`validate.py` is a shared module imported by all three pipeline scripts. It owns the `EUR_TO_USD = 1.16` constant (imported by `ingest.py` and `build.py`) and the `ValidationReport` / `ValidationError` classes. All three pipeline scripts run layered validation checks. Each check returns PASS / WARN / FAIL; a FAIL raises `ValidationError`.

| Layer | Check IDs | What it validates |
|-------|-----------|-------------------|
| Input preflight | I-1…I-8 | Required columns present, non-empty data, TAO gap ≥ 0, ADRM numeric |
| Join integrity | J-1…J-7 | AM ≥ 80% match in IAA, IAA ≥ 60% match in AM, non-prospects ≥ 50% match in TAO, no duplicate AM rows |
| Business logic | B-1…B-8 | Prospect classification, whitespace definition, currency spot-check |
| Output structure | O-1…O-7 | JSON schema, account object completeness, cluster schema, KPI cross-checks |
| Dashboard KPI | D-1…D-4 | Compact payload cross-checks (build.py) |

**Exit codes**: 0 = success, 1 = hard fail (stops pipeline), 2 = soft-block (validation warnings; output still written so downstream steps can proceed, but `run_pipeline.py` exits 2).

## Clustering Logic (`analyze.py`)

Accounts are grouped by a two-part key: `(coverage_fingerprint, whitespace_fingerprint)` — industry is intentionally excluded so cross-industry patterns cluster together:
- `coverage_fingerprint` — sorted tuple of live/project **L2** names (excluding L2s under the "Other" catch-all L1)
- `whitespace_fingerprint` — sorted tuple of whitespace **L1** names (excluding "Other")

Each account contributes to all subsets of its coverage fingerprint with size between `min_core_l2s` and `max_core_l2s` (default 2–4), so accounts sharing a partial L2 core can cluster together even if their full footprints differ.

**Post-sizing deduplication (two passes):**
1. *Identity dedup* — if two clusters share the same `(ws_fp, account_set)`, keep only the one with the larger coverage core.
2. *Whitespace-subset merge* — within each `cov_fp` group, clusters whose `ws_fp` is a superset of another cluster's `ws_fp` are absorbed into the smaller (more general) cluster; account lists are unioned. This prevents near-duplicate clusters that differ only in having extra whitespace L1s.

**Additional exclusions:** clusters with an empty whitespace fingerprint are dropped after merging.

Surviving clusters are filtered to `min_size` (default **5**), sorted by `total_gap_kusd` descending, and assigned IDs `c001`, `c002`, etc. Output is capped at `--max-clusters` (default 200).

Target L2s per cluster: `applicable_products` entries whose `sah_l1` is in the whitespace fingerprint, ranked by how many accounts in the cluster share them.

## Dashboard Architecture (`dashboard-template.html`)

The template is a self-contained Vue 3 application. `build.py` injects CDN assets and the JSON payload at build time via placeholder comments (`/*__DATA__*/`, `/*__LIB_VUE__*/`, etc.).

**Runtime globals** (set at the top of the inline script before Vue mounts):
- `DATA` — the full compact payload (`meta`, `sah_l1`, `sah_l1_short`, `sah_l2_per_l1`, `sah_hierarchy`, `accounts`, `clusters`)
- `L1` / `L1_SHORT` — arrays of SAH L1 names / abbreviations (indexed in parallel with all per-account arrays)

**Compact account object** (produced by `build.py:compact_account()`):
```
id, name, so, sg, ind, ind_b, arch, rev, iac, seg, rbc, n_sol, n_sol_b, sic, is_p,
cov[i]          — bool, live/project coverage per L1
cov_any[i]      — bool, any-status (incl. shelfware) coverage per L1
cov_products[i] — string[], products per L1
l2s[i][j]       — int per L2 under L1 i: 3=Live, 2=Project, 1=Shelfware, 0=None
l2_lpr_cnt[i][j]— int, count of logical products at each L2
tao[i]          — {gap, wallet, pri, strat, hist, acv, acv_risk, cy, cy1} or null
tao_l2[i][j]    — {gap, wallet} or null per L2 under L1 i
pipe[i]         — KUSD ADRM forecast pipeline per L1
spi[i]          — KUSD SPI planned pipeline per L1 (0.0 if no SPI data)
ws[i]           — true or null (null = covered or prospect)
prods[]         — applicable products for this account's industry
rise            — bool, account has any RISE product (LPR245/LPR943/LPR1001/LPR1052)
is_tp           — bool, account is its own SAP Top Parent CRM ID
tp_l2s[i][j]    — int (0 or 1), top-parent L2 coverage bool array
tp_name         — string or null, top-parent display name (null if account is_tp or no AM-TP data)
```

**Key Vue patterns:**
- `filteredAccounts` (computed) — applies all global filters; every render method reads from this, not `DATA.accounts`
- `effectiveWs(a)` (method) — returns `a.ws` with shelfware-only L1s nulled out (`cov_any[i] && !cov[i]`); use this everywhere instead of bare `a.ws`
- `kpis` (computed) — sums total whitespace gap across all whitespace cells; `renderTopAccountsTable` must match this definition
- `quarterLabel` (computed) — derives `Q1 2026` etc. from `DATA.meta.generated_at`; never hardcode quarter strings
- Render methods (`renderHeatmap`, `renderMatrix`, etc.) write directly to DOM via `innerHTML`; all data-derived strings must be passed through `esc()` to prevent XSS
- Charts use Chart.js 4 + chartjs-chart-treemap; chart instances are stored in the `charts` map and destroyed before re-creation via `destroyChart(id)`

**Cluster list filter behavior (`renderPortfolioList`):** The Solution Area (`selectedL1`) filter gates clusters against `c.ws_l1s` directly — a cluster is included if the selected L1 is in its whitespace fingerprint, and account counts remain unchanged. Other filters (office, group, industry, etc.) still intersect cluster members with `filteredAccounts`, reducing visible account counts within surviving clusters. This means `selectedL1` never fragments cluster membership; other filters do.
